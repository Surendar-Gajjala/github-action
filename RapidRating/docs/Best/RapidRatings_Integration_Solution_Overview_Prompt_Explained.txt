RapidRatings Integration - Solution Overview Prompt: What It Is and What It Is For
==================================================================================

File explained: RapidRatings_Integration_Solution_Overview_Prompt.md (same folder)
Written: 2026-10-30


1. WHAT THIS FILE IS
--------------------
The file is a PROMPT, not a design document. It is a detailed set of instructions
to give an AI assistant (or a solution architect) so that it writes ONE specific
document: "RapidRatings Integration - Solution Overview" for the Z2 Enterprise
Data Integrations program.

It does not describe the solution itself. It describes what the solution document
must contain, which source material it must use, how it must be structured, and
which mistakes it must not make.


2. THE GOAL
-----------
To produce a solution overview that a design-review board and the developers
taking over the work can rely on. After reading the generated document, a
reviewer should understand:

  - how a Z2 customer enables RapidRatings for a tenant and enters credentials;
  - how Z2 authenticates to RapidRatings (OAuth 2.0 Client Credentials,
    server-side only, token cached and renewed before expiry);
  - which RapidRatings APIs are called and in what order
    (Portfolios -> Companies -> rrid -> Periods and Ratings);
  - the complete source schemas of Company, Periods and Ratings;
  - how every source property maps into the existing Z2 Company DataModel;
  - how the data appears on the Company Details page and in Raw Properties;
  - how schema synchronization and data synchronization (manual and scheduled)
    work;
  - security, validation and error handling;
  - which decisions are made, and which questions remain open before production.

The second, equally important goal is ACCURACY. Most of the prompt exists to stop
the writer from inventing things: API parameters, token fields, pagination,
platform configuration syntax or UI behaviour that nobody has confirmed.


3. HOW THE PROMPT IS ORGANISED
------------------------------

4. THE ACCURACY RULES IN SHORT
------------------------------
  - Treat the supplied endpoints and property lists as source material, not as
    proof of every runtime behaviour.
  - Keep every source property name and type; never drop a property silently.
    If something is not mapped, say why.
  - A field seen only as null (e.g. industryClassificationCode, externalSourceId,
    financialAssets, cashFromOperationsFromCashFlow) has an UNRESOLVED type.
  - Never convert null to zero, rescale "millions", or convert currencies.
  - Never merge latestRatings and the Ratings endpoint silently when they differ.
  - Never join records by company name, array position or response order.
  - Do not assume nested objects inside a PROPS_ARRAY are supported; flatten
    termPd.year2 ... termPd.year10 if needed.
  - Label every statement as one of: verified from samples, proposed design
    decision, or needs confirmation.
  - Keep it a solution overview, not a low-level implementation specification.


5. HOW TO USE IT
----------------
  1. Give the whole prompt file to the AI assistant (or the architect).
  2. Attach the supporting material it refers to: the sample API responses and
     the existing Company DataModel (docs/A1company.json).
  3. Check the result against the required 14 headings (prompt section 15) and
     the accuracy rules (prompt section 16).
  4. Review the open-questions table with the product owner and RapidRatings
     before implementation starts.

7. PARTS OF THE PROMPT THAT ARE NOW OUT OF DATE
-----------------------------------------------
The prompt was written before the sandbox APIs were tested. Several things it
tells the writer to treat as "unknown, to be confirmed" have since been observed
in the sandbox (2026-10-28, see docs/api/). A document generated from the prompt
today may describe them as open when they are in fact known for the sandbox:

  - Token response fields: access_token, expires_in (1800 = 30 min),
    token_type "Bearer", scope. No refresh token is issued.
  - Expired or invalid token: 403 on the data API, 401 on the Outreach API.
  - Pagination: page + next URL; companies 20 per page, periods and ratings 10
    per page, all fixed; newest first. Asking for a page past the end returns
    404 (companies) or 500 (others), so only follow "next".
  - Supported company filters: portfolio, name (3+ characters), ticker,
    externalSourceId. Any unknown query parameter returns 400.
  - No incremental "changed since" filter exists.
  - Rating id equals the period id (e.g. 2019YE), one rating per period.
  - probabilityDefault and termPd values are percentages; fhr and chs are 0-100;
    leverage, liquidity and earningsPerformance were Strong / Average / Weak.
  - The company DETAIL endpoint also returns reports[] and sectorAverages, which
    the prompt's Company property list does not include.
  - Outreach: separate host, has an OpenAPI spec, uses the same token, and
    creating a request sends real emails to the counterparty.

These are sandbox observations; production still has to be confirmed. If the
prompt is reused, give the writer docs/api/ as well, and tell it to present these
items as "verified in the sandbox" rather than as open questions.

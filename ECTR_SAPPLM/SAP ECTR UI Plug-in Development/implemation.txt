------------------------------------------------------------------------------------------
A.1  THE THREE LAYERS IN ONE SENTENCE EACH
------------------------------------------------------------------------------------------

  1. BUSINESS CODE   (api + core)  Plain Java 17. Knows nothing about ECTR, Felix or Maven.
                                   It only talks to 5 small interfaces ("ports").
  2. OSGi PLUMBING   (bnd + Felix + SCR)  Turns the jars into bundles, creates the objects
                                   and wires them together at runtime from annotations.
  3. HOST            (mock now, ECTR later)  Implements the ports that read data / show
                                   messages, and calls the ports for "save" and "drop".

  Rule of thumb: if you change a business rule you touch only core; if you change how
  ECTR is reached you touch only the adapter; if a bundle does not start you look at
  layer 2 (manifest, resolver, scr:info).


------------------------------------------------------------------------------------------
A.2  THE TOOL CHAIN AT BUILD TIME                                               [VERIFIED]
------------------------------------------------------------------------------------------

  mvnw / mvnw.cmd
     |  downloads Maven 3.9.9 on first use, then runs it with your JDK 17
     v
  Maven reactor   builds modules in dependency order: api -> core -> mock -> runtime
     |
     |   for api, core and mock (each one is a bundle):
     |     maven-compiler-plugin   .java -> .class (release 17)
     |     bnd-maven-plugin        reads the classes + OSGi annotations and writes
     |       (goal bnd-process)      META-INF/MANIFEST.MF
     |                               OSGI-INF/<component class>.xml        (DS descriptors)
     |                               OSGI-INF/metatype/<Config class>.xml  (config schema)
     |     maven-surefire-plugin   runs the JUnit 5 tests (phase "test")
     |     maven-jar-plugin        zips target/classes, using bnd's manifest unchanged
     |
     |   for runtime (packaging "pom", no Java code):
     |     bnd-resolver-maven-plugin   ectr.bndrun "-runrequires" + the jars listed as
     |       (phase package)           dependencies in the runtime pom
     |                                 -> computes the full "-runbundles" list and writes
     |                                    it back into ectr.bndrun
     |     bnd-export-maven-plugin     -> target/ectr.jar (launcher + Felix + all bundles)
     |     bnd-run-maven-plugin        optional: start the same runtime from Maven
     v
  ectr-plugin-runtime/target/ectr.jar   one executable jar, about 2 MB

  Important: the OSGi annotation jars (osgi.annotation, ...component.annotations,
  ...metatype.annotations) are "provided" scope. bnd reads them at BUILD time and turns
  them into the manifest and XML above. They are not needed at runtime.

  bnd resolver                proves all bundles fit together;     ectr.bndrun, export
                              fills -runbundles

                              loader per bundle, resolve,

                              injects references and Config.

                              org.osgi.util.promise, ...function

                              runtime: supplies config values      ValidationSaveInterceptor,
                              per PID (Phase 13)                   MockEctrSession
  java.lang.System.Logger     logging without a dependency;        console / ECTR log
                              routed to java.util.logging; the

  How the manifest connects the bundles (you can see it with
  unzip -p ectr-plugin-core/target/ectr-plugin-core-1.0.0-SNAPSHOT.jar META-INF/MANIFEST.MF):
     api   Export-Package: ...api.model;version=1.0.0, ...api.port;version=1.0.0
     core  Import-Package: ...api.model;version="[1.0,2)", ...api.port;version="[1.0,2)"
           Service-Component: OSGI-INF/...RuleRepository.xml, ...  (tells SCR what to create)
           Require-Capability: osgi.service;(objectClass=...EctrSession);effective:=active
                               (and the same for ObjectPropertyReader, UserNotifier)
     mock  Import-Package: the api packages only
  The "osgi.service" requirements are why ectr.bndrun sets "-resolve.effective: active":
  the resolver must find a bundle that PROVIDES EctrSession etc. Locally that is the mock;
  in ECTR it will be the SAP adapter.

A.4  WHAT HAPPENS WHEN YOU RUN  java -jar ectr.jar                              [VERIFIED]
------------------------------------------------------------------------------------------

  1. The bnd launcher inside ectr.jar starts Felix with the -runproperties of ectr.bndrun:
       org.osgi.framework.storage.clean=onFirstInit   fresh felix-cache on every start
       java.util.logging.SimpleFormatter.format=...   "INFO <logger>: <message>" lines
  2. Felix installs the 10 -runbundles (11 with the system bundle) and RESOLVES each one:
       every Import-Package must match an Export-Package with a compatible version, and
       Require-Capability osgi.ee=JavaSE 17 must match the running JVM.
       Missing match -> bundle stays INSTALLED (see Phase 18).
  3. Felix starts the bundles -> ACTIVE. Our bundles have NO BundleActivator.
  4. SCR (itself a bundle) sees the Service-Component header of core and mock, reads the
     OSGI-INF/*.xml files and registers 7 components.
  5. A component becomes SATISFIED when every mandatory @Reference has a service.
     scr:list shows SATISFIED (not ACTIVE) right after start: these components are
     "delayed", so SCR creates the object the first time somebody uses the service.
     That is why the log line "Rules loaded (...)" appears only on the first ectr:save or
     ectr:drop, not at start-up.
  6. When it is created, SCR calls the @Activate CONSTRUCTOR with the injected services and
     a Config object (annotation defaults, or Configuration Admin values when present).
  7. Gogo sees the service of EctrShellCommands, whose properties are
     osgi.command.scope=ectr and osgi.command.function=list,show,save,drop,lang,demo,
     and offers them as ectr:list, ectr:show, ... at the g! prompt.

A.5  COMPONENT WIRING: WHO GETS INJECTED INTO WHOM                              [VERIFIED]
------------------------------------------------------------------------------------------

  Each arrow means "is injected into the @Activate constructor of".

   ectr-plugin-mock (host side)                 ectr-plugin-core (plug-in side)
   ----------------------------                 -------------------------------
                                                RuleRepository
                                                  (no references, only Config;
                                                   loads both rule XML files)
                                                     |            |
   MockEctrSession ----- EctrSession ----------------+---> ValidationSaveInterceptor
   ConsoleNotifier ----- UserNotifier ---------------+--->   (service SaveInterceptor)
                                                     |
   MockObjectRepository - ObjectPropertyReader -+    +---> ObjectBrowserDropHandler
   MockEctrSession ----- EctrSession -----------+------->   (service DropHandler)
   ConsoleNotifier ----- UserNotifier ----------+    RuleRepository ---^

   EctrShellCommands  <--- MockObjectRepository, MockEctrSession,
     (the fake client)     ALL SaveInterceptor services (cardinality MULTIPLE),
                           ALL DropHandler services     (cardinality MULTIPLE)

  So the dependency goes in both directions THROUGH THE PORTS ONLY:
    core USES     ObjectPropertyReader, EctrSession, UserNotifier  (host implements them)
    core PROVIDES SaveInterceptor, DropHandler                     (host calls them)
  core never imports a mock class, and the mock never imports a core class.

  Configuration PIDs (all optional, defaults in the code):
    com.example.ectr.plugin.rules         validationRulesFile, packagingRulesFile  (core)
    com.example.ectr.plugin.validation    blockOnViolation = true                  (core)
    com.example.ectr.plugin.mock.session  userId = DEMO_USER, language = en        (mock)

A.6  TRACE 1:  g! ectr:save PRT-001                                             [VERIFIED]
------------------------------------------------------------------------------------------

   #  Class (module)                          What happens
   -- --------------------------------------  ---------------------------------------------
   1  Gogo -> EctrShellCommands.save (mock)   the "user clicked Save"
   2  MockObjectRepository.read (mock)        -> Optional<EngineeringObject> PRT-001 (PART)
                                              (real life: adapter maps the ECTR object)
   3  ValidationSaveInterceptor.beforeSave    called once per registered SaveInterceptor
      (core)
   4  RuleRepository.validator()              the MetadataValidator built at activation
   5  MetadataValidator.validate              RuleSet.rulesFor(PART) -> 7 rules from
                                              validation-rules.xml
   6  each ValidationRule.check               MandatoryFieldRule x4, PatternRule x2,
                                              RequiredLanguagesRule x1
                                              -> 3 Violations (ruleId + LocalizableMessage)
   7  ValidationResult.isValid() = false
   8  Messages(Support.safeLocale(session))   translate keys in the SESSION language:
                                              save.blocked + TypeLabel(PART) -> "part",
                                              validation.mandatory + FieldLabel(WEIGHT_KG)
                                              -> "Weight (kg)", ...
   9  System.Logger INFO                      "PRT-001: 3 validation violation(s)
                                              [mandatory:WEIGHT_KG, pattern:REVISION,
                                              description-languages], save blocked"
  10  ConsoleNotifier.error (mock)            prints "[user ERROR] Cannot save part ..."
  11  return SaveDecision.reject(lines)
  12  EctrShellCommands                       allowed == false ->
                                              "=> SAVE OF PRT-001 CANCELLED"

  If step 3-8 throws a RuntimeException: Support.newIncidentReference() -> ECTR-XXXXXXXX,
  stack trace to the log, "save.internalError" to the user, SaveDecision.reject
  (FAIL CLOSED). With blockOnViolation=false step 10/11 become notifier.warn +
  SaveDecision(true, lines).

A.7  TRACE 2:  g! ectr:drop FLD-PACK ASM-100                                    [VERIFIED]
------------------------------------------------------------------------------------------

   1  EctrShellCommands.drop (mock)           builds DropEvent([ASM-100], FLD-PACK, COPY)
                                              (COPY is the default action)
   2  ObjectBrowserDropHandler.onDrop (core)  delegates to its DragDropController
   3  DragDropController.handle               reader.read(target) -> FOLDER,
                                              reader.read(each source) -> ASSEMBLY
   4  dropOntoFolder                          all sources are assemblies -> continue
   5  validateStructures                      reader.structure(ASM-100).allObjectIds()
                                              -> every object is read and run through the
                                              SAME MetadataValidator as in Trace 1
   6  PackagingRuleEngine.plan("ASM-100")     collect: leaf parts, quantity multiplied
                                              along the path; drawings of every node via
                                              findDrawingsFor
                                              rules sorted by phase:
                                                SameMaterialGroupRule   GROUP   MG-<group>
                                                IncludeDrawingsRule     ENRICH  drawings
                                                MaxComponentCountRule   SPLIT   max = 3
                                              leftovers -> UNASSIGNED
                                              -> PackagingPlan(rootId, packages, warnings)
   7  DragDropResult(accepted=true,           messages = drop.packagingCreated +
                     messages, plans)         one drop.packageLine per package
   8  ObjectBrowserDropHandler                Messages translates, LOG INFO
                                              "Drop [ASM-100] -> FLD-PACK (COPY): accepted",
                                              ConsoleNotifier.info, DropOutcome(true, lines)
   9  EctrShellCommands                       "=> DROP EXECUTED (simulated)"

  Real output:

                     Package MG-CAST: PRT-101, PRT-111, DRW-101
                     Package MG-MACHINED: PRT-102

------------------------------------------------------------------------------------------
PHASE 1 - DESIGN DECISION: PORTS AND ADAPTERS                                   [VERIFIED]
------------------------------------------------------------------------------------------

Step 1.1  Problem: we have no SAP ECTR SDK, and must not invent ECTR class names or events.

Step 1.2  Solution: put ALL host access behind our own small interfaces ("ports").
          - Business logic (core) depends only on these interfaces and the JDK.
          - For local work, a mock bundle implements them.
          - Later, a real adapter bundle (ectr-plugin-sap) implements them with the ECTR SDK.

              ECTR client  <-->  ectr-plugin-sap (later)  -->  ectr-plugin-api  <--  ectr-plugin-core
                                 ectr-plugin-mock (now)   -->  ectr-plugin-api

          Benefits:
          - no guessing about ECTR APIs: core never imports an ECTR class
          - fast tests: 63 unit tests run in seconds on any machine
          - release-proof: when ECTR changes its API, only the adapter changes

Step 1.3  Module plan (Maven multi-module):
              ectr-plugin-api      model + ports (exported packages)
              ectr-plugin-core     validation, packaging, drag-and-drop, i18n, DS components
                                   (exports NOTHING; internals stay private)
              ectr-plugin-mock     in-memory "fake ECTR" + shell commands      [ILLUSTRATIVE]
              ectr-plugin-runtime  Felix runtime packaged as ectr.jar

PHASE 3 - API BUNDLE (ectr-plugin-api)                                          [VERIFIED]
------------------------------------------------------------------------------------------

Step 3.1  Create the model package  com.example.ectr.plugin.api.model
          - ObjectType          enum: PART, ASSEMBLY, DRAWING, FOLDER
          - PropertyKey         logical property names: MATERIAL_GROUP, MATERIAL,
                                WEIGHT_KG, REVISION, CAD_FILE, STATUS, REFERENCED_OBJECT
                                (OUR names. The adapter maps the real SAP fields onto them.)
          - LocalizedText       record: Map<Locale,String> for multilingual descriptions
                                - keys are normalised to the language only (de_DE -> de)
                                - get(locale), getOrFallback(locale, ENGLISH), languages()
          - EngineeringObject   record: id, type, properties, description (immutable)
                                - property(key) returns Optional; blank counts as missing,
                                  values are trimmed
                                - properties are Strings only; rules check formats by regex
          - CadStructureNode    record: objectId, quantity (>= 1), children (assembly tree)
                                - leaf(), isLeaf(), walk(visitor), allObjectIds()

Step 3.2  Create the port package  com.example.ectr.plugin.api.port             [ILLUSTRATIVE]
          - ObjectPropertyReader  Optional<EngineeringObject> read(id)  (empty if unknown)
                                  CadStructureNode structure(rootId)    (leaf for a part)
                                  List<String> findDrawingsFor(id)
                                  Implementations must be thread-safe.
          - SaveInterceptor       beforeSave(object) -> SaveDecision(allowed, messages)
                                  SaveDecision.allow() / SaveDecision.reject(messages);
                                  messages may be non-empty even when allowed (warn mode)
          - DropHandler           onDrop(DropEvent) -> DropOutcome(accepted, messages)
          - DropEvent             record(sourceIds, targetId, action); needs >= 1 source
          - DropAction            COPY, MOVE, LINK
          - UserNotifier          info / warn / error (texts are already localized)
          - EctrSession           userId(), locale()

          Direction of each port:
              ObjectPropertyReader, EctrSession, UserNotifier   core -> host (host implements)
              SaveInterceptor, DropHandler                      host -> core (host calls)

Step 3.3  Export both packages with package-info.java:
              @org.osgi.annotation.bundle.Export
              @org.osgi.annotation.versioning.Version("1.0.0")

Step 3.4  Build and inspect the manifest:
              mvnw -f ectr-plugin-api/pom.xml package
              unzip -p ectr-plugin-api/target/ectr-plugin-api-1.0.0-SNAPSHOT.jar META-INF/MANIFEST.MF
          Expected: "Export-Package: ...api.model;version=1.0.0, ...api.port;version=1.0.0"
          and "Require-Capability: osgi.ee;filter:=(&(osgi.ee=JavaSE)(version=17))".


------------------------------------------------------------------------------------------
PHASE 4 - CORE: MESSAGES AND XML INFRASTRUCTURE                                 [VERIFIED]
------------------------------------------------------------------------------------------

Step 4.1  i18n package
          - LocalizableMessage  record(key, args). Rules return keys, not text.
                                Helper args: FieldLabel(propertyKey), TypeLabel(enum).
                                A LocalizableMessage can also be an argument (nested).
          - Messages            wraps ResourceBundle. Uses the session locale, NOT the JVM
                                default locale (no-fallback control). Translates nested
                                messages and labels (field.<KEY>, type.<TYPE>).
                                Passes the bundle's own class loader explicitly, so it
                                works inside OSGi.
                                A missing key is shown as "key [args]" instead of failing.
          - messages.properties      (English base)
          - messages_de.properties   (German, UTF-8)
          Rules for writing message texts:
            - a literal apostrophe is written ''
            - leading spaces are written '  ' (java.util.Properties strips unquoted spaces)
            - plurals use {0,choice,1#1 object|1<{0} objects}

Step 4.2  config package
          - RuleConfigurationException
          - SecureXml   JAXP DOM parser hardened against XXE: DOCTYPE disallowed,
                        external entities off. It loads either an external file path or
                        the default resource packaged in the bundle.


------------------------------------------------------------------------------------------
PHASE 5 - CORE: MANDATORY-FIELD VALIDATION                                      [VERIFIED]
------------------------------------------------------------------------------------------

Step 5.1  Create the rule interface and result types (package ...core.validation):
              ValidationRule     id(), check(object) -> Optional<Violation>
              Violation          objectId, ruleId, propertyKey (null for object-level
                                 rules), LocalizableMessage
              ValidationResult   list of violations, isValid(), merge()

Step 5.2  Implement the rules:
              MandatoryFieldRule      value must exist and not be blank
              PatternRule             if a value exists, the whole value must match the regex
              RequiredLanguagesRule   description needed in each listed language
          PatternRule ignores empty values on purpose: combine it with <mandatory> so the
          user gets one clear message ("mandatory") instead of two.

Step 5.3  RuleSet (rules per ObjectType) and MetadataValidator (runs all rules and
          collects ALL violations, so the user can fix everything at once).

Step 5.4  RuleSetLoader reads src/main/resources/rules/validation-rules.xml:
              <validation-rules>
                <object-type name="PART">
                  <mandatory property="MATERIAL_GROUP"/>
                  <mandatory property="MATERIAL"/>
                  <mandatory property="WEIGHT_KG"/>
                  <pattern   property="WEIGHT_KG" regex="\d{1,6}(\.\d{1,3})?" example="12.5"/>
                  <mandatory property="REVISION"/>
                  <pattern   property="REVISION" regex="[A-Z]{1,2}" example="A, B ... ZZ"/>
                  <description-languages required="en,de"/>
                </object-type>
                <object-type name="ASSEMBLY"> REVISION mandatory + pattern, en,de </object-type>
                <object-type name="DRAWING">  REFERENCED_OBJECT, REVISION, en     </object-type>
                <!-- FOLDER has no rules: folders are never validated. -->
              </validation-rules>
          The loader fails with a clear message on any of these, so a typo can never
          silently disable a check:
            - unknown element
            - unknown object type
            - duplicate object type
            - bad regex
            - missing attribute
            - <!DOCTYPE> / external entities (XXE)


------------------------------------------------------------------------------------------
PHASE 6 - CORE: ASSEMBLY PACKAGING RULES                                        [VERIFIED]
------------------------------------------------------------------------------------------

Step 6.1  Create the PackagingRule interface: id(), phase(), apply(context).
          The phases run in this order:
              GROUP   put components into packages
              ENRICH  add related objects (drawings) to packages
              SPLIT   reshape packages after their content is final
          Sorting by phase means a misordered XML file cannot, for example, split packages
          before the drawings were added.

Step 6.2  PackagingContext holds the working state of one run: root, leaf components,
          total quantities, drawings, packages (name -> ids) and warnings.
          Helpers used by rules: components(), isPackaged(id), addToPackage(name, id), warn().

Step 6.3  PackagingRuleEngine.plan(rootId):
          1. read the root and its CAD structure through ObjectPropertyReader
             (unknown root -> NoSuchElementException)
          2. collect the leaf components, multiplying quantities along the path
             (2 x SUB, each with 3 x P  ->  6 x P)
          3. collect the drawings of every node; unreadable objects become warnings
          4. sort the rules by phase (stable sort) and apply them
          5. put anything left over into package "UNASSIGNED" (nothing is lost)
          6. return a PackagingPlan(rootId, packages, warnings)

Step 6.4  Implement the sample rules (the business meaning is ILLUSTRATIVE; replace it
          with the client's policy):
              SameMaterialGroupRule   (GROUP)   package "MG-<group>"; no group -> warning,
                                                part ends up in UNASSIGNED
              IncludeDrawingsRule     (ENRICH)  drawing joins the package of its
                                                REFERENCED_OBJECT, else "DOCUMENTATION"
              MaxComponentCountRule   (SPLIT)   NAME-1, NAME-2, ... when size > max

Step 6.5  PackagingRulesLoader reads rules/packaging-rules.xml:
              <packaging-rules>
                <rule id="group-by-material-group"/>
                <rule id="include-drawings"/>
                <rule id="max-components-per-package" max="3"/>
              </packaging-rules>
          An unknown rule id fails loading and lists the allowed ids.

Step 6.6  A PackagingPlan is a PROPOSAL (package name -> object ids, plus warnings).
          Saving it in SAP is not part of this project (see Phase 17.7).


------------------------------------------------------------------------------------------
PHASE 7 - CORE: DRAG-AND-DROP BUSINESS RULES                                    [VERIFIED]
------------------------------------------------------------------------------------------

Step 7.1  DragDropResult: accepted, messages (LocalizableMessage), packaging plans.

Step 7.2  DragDropController.handle(DropEvent) applies these rules:
          - unknown target or source  -> reject (drop.unknownObject)
          - target FOLDER:
              * only assemblies are allowed (drop.onlyAssembliesToFolder)
              * validate EVERY object in each structure; reject with details if invalid
                (drop.invalidSource + one drop.violationLine per violation)
              * otherwise build a packaging plan for each assembly -> accept
                (drop.packagingCreated + drop.packageLine per package)
          - target ASSEMBLY:
              * reject a cycle (source == target, or the target is in the source structure)
                (drop.cycle)
              * validate the sources and their structures -> accept (drop.linkAccepted)
                or reject
          - target PART or DRAWING -> reject (drop.unsupportedTarget)
          Every rejection includes the reason. A refused drop with no explanation is the
          most common complaint about UI customisations.

Step 7.3  Validation in a drop uses the SAME MetadataValidator as the save check, so an
          object that cannot be saved cannot be packaged either.

PHASE 8 - CORE: OSGi DECLARATIVE SERVICES COMPONENTS                            [VERIFIED]
------------------------------------------------------------------------------------------

Step 8.0  Common pattern for all components:
          - @Component on the class, @Activate on the CONSTRUCTOR (DS 1.4+)
          - @Reference on constructor parameters: static, mandatory references, so the
            component starts only when all of its services exist
          - @Designate(ocd = Config.class) + an @ObjectClassDefinition @interface Config
            with defaults in the code; overridable through Configuration Admin by PID
          - the class stays immutable, and unit tests simply call "new ...(...)" without
            starting any framework

Step 8.1  RuleRepository                      @Component, PID com.example.ectr.plugin.rules
          - Metatype config: validationRulesFile, packagingRulesFile (empty = bundled)
          - loads both XML files once and shares them: validator(), packagingRules()
          - broken XML -> logs ERROR and activation fails, so dependent components stay
            unsatisfied (fail fast, visible in scr:info)
          - a configuration change re-creates the component, which reloads the files
          - RuleRepository.bundledDefaults() builds it without OSGi (tests, non-OSGi host)

Step 8.2  ValidationSaveInterceptor           @Component(service = SaveInterceptor.class)
          - PID com.example.ectr.plugin.validation
          - constructor injection: RuleRepository, EctrSession, UserNotifier, Config
          - config: blockOnViolation (default true; false = warning-only roll-out)
          - valid    -> SaveDecision.allow()               (log DEBUG)
          - invalid  -> localized list -> UserNotifier.error -> SaveDecision.reject
                        (warning mode: UserNotifier.warn -> SaveDecision(true, lines))
                        (log INFO with object id and rule ids)
          - crash    -> incident reference ECTR-XXXXXXXX logged with stack trace,
                        save BLOCKED (fail closed)

Step 8.3  ObjectBrowserDropHandler            @Component(service = DropHandler.class)
          - constructor injection: ObjectPropertyReader, RuleRepository, EctrSession,
            UserNotifier
          - builds a DragDropController from the reader, validator and packaging engine
          - translates the result into the session language and notifies the user
            (accepted -> info, rejected -> warn)
          - on a crash it handles errors the same way as Step 8.2 (incident reference, drop cancelled)

Step 8.4  Support helper: newIncidentReference(), safeLocale(session) (English fallback,
          logs a WARNING if the session cannot tell the language).

Step 8.5  Logging uses java.lang.System.Logger. That adds no dependency.
          Levels:  ERROR   = needs support
                   WARNING = degraded but working
                   INFO    = one line per user decision (save blocked/allowed, drop
                             accepted/rejected)
                   DEBUG   = passed validations
          Log object ids and rule ids, never full property maps (confidential engineering
          data) and never credentials.

Step 8.6  Three audiences, three channels:
              engineer        -> UserNotifier         localized, actionable, only the
                                                      incident reference as an id
              support / dev   -> System.Logger        ids, rule ids, stack traces
              host / caller   -> SaveDecision /       allowed / accepted + the same lines
                                 DropOutcome
          Business-rule violations are RESULTS, not exceptions. Only unexpected errors are
          exceptions, and they always end in a blocked action.

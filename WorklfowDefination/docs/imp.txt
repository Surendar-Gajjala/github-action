# Project: Supply Chain Management — Item & Part Lifecycle Workflow Engine

## 1. Project Objective

Build a full-stack Supply Chain Management (SCM) application using **Java 17 or 21, Spring Boot, React, TypeScript, H2 database, and Camunda 8 workflow orchestration**.

The application manages Items and their related Parts. Whenever an Item or its Parts are changed, the Item must go through a configurable lifecycle approval workflow before its status can become `APPROVED`.

The application must have exactly three main navigation tabs:

1. **Items**
2. **Parts**
3. **Workflow**

The Workflow tab must contain the workflow definition management interface, including workflow definitions, lifecycle stages, approval rules, active workflow instances, and workflow execution history.

Do not use Docker or Docker Compose. Use a locally runnable development environment.

## 4. Data Model and Relationships

### Item entity

Create an `Item` entity with:

- `id`: Long
- `itemNumber`: String, unique, required
- `name`: String, required
- `description`: String
- `lifecycleStatus`: Enum
- `revision`: String
- `createdAt`: LocalDateTime
- `updatedAt`: LocalDateTime
- `version`: Long, for optimistic locking

Lifecycle status values:

- `DRAFT`
- `IN_REVIEW`
- `APPROVED`
- `REJECTED`
- `CHANGE_PENDING`

### Part entity

Create a `Part` entity with:

- `id`: Long
- `partNumber`: String, unique, required
- `name`: String, required
- `description`: String
- `partType`: String
- `createdAt`: LocalDateTime
- `updatedAt`: LocalDateTime
- `version`: Long, for optimistic locking

### Item-Part relationship

Implement a many-to-many relationship between Items and Parts.

One Item can contain multiple Parts, and one Part can be associated with multiple Items.

Create an explicit join entity or join table with appropriate foreign keys and uniqueness constraints.

Use an explicit relationship entity if relationship metadata such as quantity or position may be needed later.

Example:

- Item: `ITEM-1001`
- Name: `Hydraulic Pump Assembly`
- Parts: `PART-101`, `PART-102`, `PART-103`

The Items page must display the associated Parts in the Item details view.

### Item creation and editing

Users must be able to add or remove Parts from the selection.

Example:

Item: Hydraulic Pump Assembly

Selected Parts:
- Shaft
- Bearing
- Housing

### Lifecycle rules

A new Item starts in `DRAFT`.

When the user modifies an existing Item or changes its Part relationships, mark the Item as requiring lifecycle review.

If the Item is already approved, set its status to `CHANGE_PENDING` when a relevant change is made.

Do not allow a modified Item to continue appearing as the current approved revision.

Preserve the last approved revision or approved snapshot until the new revision is approved.

When the user submits the changes, start the configured lifecycle workflow and set the applicable revision or change request to `IN_REVIEW`.

The Item must not become `APPROVED` merely because the user edited or saved the form.

## 7. Workflow Tab — Workflow Definition Engine

The Workflow tab is a core feature, not just a workflow history screen.

Implement the following sections inside the Workflow tab:

### A. Workflow Definitions

- Actions

- View Instances
- View Version History

Example workflow definitions:

- `ITEM_LIFECYCLE_APPROVAL`
- `ITEM_PART_CHANGE_APPROVAL`
- `ITEM_REVISION_RELEASE`

### B. Workflow Definition Designer

Provide a visual, configurable workflow designer for defining lifecycle stages and transitions.

Use a BPMN 2.0-compatible designer, such as bpmn-js, where feasible.

Allow users to define:

- Start event
- Validation service task
- Manager approval task
- Engineering approval task
- Conditional gateway
- Rejection path
- Revision release task
- End event

Example process:

Start
→ Validate Item
→ Validate Part Relationships
→ Engineering Approval
→ Manager Approval (when required)
→ Release Approved Revision
→ End

Rejection path:

Approval Rejected
→ Record Rejection Reason
→ Return to Draft or Change Pending
→ End

A user must be able to configure approval requirements and conditional transitions rather than hardcoding every process into the React frontend.

### C. Lifecycle State Configuration

Configure permitted lifecycle transitions.

Example:

- `DRAFT` → `IN_REVIEW`
- `IN_REVIEW` → `APPROVED`
- `IN_REVIEW` → `REJECTED`
- `REJECTED` → `DRAFT`
- `APPROVED` → `CHANGE_PENDING`
- `CHANGE_PENDING` → `IN_REVIEW`

Only valid transitions may be executed.

Lifecycle state configuration and BPMN workflow execution are related but distinct. Enforce lifecycle transition rules in the backend as well as in the workflow process.

### D. Approval Tasks

- Task Name
- Item Number

- Workflow Instance ID
- Assigned User or Role

- Created At
- Due Date, if configured
- Actions

Actions:

- Approve
- Reject
- View Item Changes
- View Parts Changes
- View Workflow History

Require a rejection reason when rejecting a request.

Enforce authorization on the backend so only authorized users can complete approval tasks.

### E. Running Workflow Instances

Display active workflows with:

- Workflow Instance ID
- Workflow Definition
- Business Key
- Item Number
- Current Stage
- Status
- Started At
- Last Updated

Allow authorized users to view execution details and audit history.

Do not allow users to bypass required approval stages by directly changing the Item status.

### F. Workflow History

Track:

- Workflow started
- Item submitted
- Parts added or removed
- Approval requested
- Approval completed
- Request rejected
- Revision released
- Workflow failed

Store actor, timestamp, action, business key, workflow instance ID, and relevant change summary.

## 8. Camunda 8 Integration

Use Camunda 8 as the actual workflow orchestration engine.

Implement a clear integration boundary:

- `WorkflowService`
- `WorkflowDefinitionService`
- `WorkflowInstanceService`
- `WorkflowTaskService`
- `CamundaWorkflowAdapter`
- `WorkflowWorker` components

Use the supported Camunda 8 APIs and deployment model for the selected version.

The backend must:

1. Deploy or publish BPMN workflow definitions.
2. Start a process instance using the selected workflow definition.
3. Pass the Item ID, change request ID, actor, and business key as process variables.
4. Execute validation and revision-release work through service workers.
5. Handle approval tasks and completion.
6. Persist business audit events in H2.
7. Reflect workflow execution status in the UI.
8. Handle retries and workflow incidents.
9. Prevent duplicate workflow starts for the same submitted change request.
10. Reconcile workflow completion with the application's lifecycle state.

Use a stable business key, such as the Item ID plus a unique change request ID.

### Important lifecycle consistency rule

The workflow engine coordinates the approval process, but the backend must own the authoritative lifecycle state transition.

Only the successful completion of all required approval stages may trigger the approved revision release.

Use optimistic locking, idempotent workers, and transactional business updates to prevent concurrent or duplicate approvals.

Do not use a direct SQL update or an unrestricted REST endpoint to mark an Item as approved.

## 12. Example End-to-End Business Scenario

1. Create Item `ITEM-1001`, named `Hydraulic Pump Assembly`.
2. Select Parts `PART-101`, `PART-102`, and `PART-103` using the dropdown.
3. Save the Item as `DRAFT`.
4. Open the Workflow tab and publish `ITEM_LIFECYCLE_APPROVAL`.
5. Submit the Item for approval.
6. Camunda 8 starts a workflow instance.
7. The workflow validates the Item and its Part relationships.
8. The Engineering Approver reviews the change.
9. The Manager approves if required by the workflow definition.
10. The revision-release worker checks that all required approvals are complete.
11. The backend releases the approved revision and sets the lifecycle status to `APPROVED`.
12. The Items tab shows the approved status and the associated Parts.
13. Workflow History shows each transition, actor, timestamp, and decision.

Now edit the approved Item and remove `PART-103`.

14. The backend creates a new change request and marks the change as pending.
15. The previously approved revision remains available as the last approved revision.
16. Submit the new change request for approval.
17. The workflow executes again.
18. The Item becomes `APPROVED` for the new revision only after all required approvals succeed.
